# 0.2.7 — 上传性能本地预览 / Local upload performance preview

本版先安装到本机测试，尚未发布社区。最低 Obsidian 1.11.4。保留 0.2.6 传输中心，配置、授权、库绑定和云端格式兼容。
This is a local preview, not a community release. Requires Obsidian 1.11.4+. Includes the 0.2.6 transfer center; configuration, authorization, bindings and cloud format remain compatible.

## 使用与行为

- 设置 → VaultSail → 传输与恢复 → **单文件分片并发**：电脑默认 **2**，可选 **1–4**，下次任务生效。设为 1 可对照原来的串行分片。移动端固定为 1。
- 文件并发仍默认 8，可选 1–32；同一 Vault 的百度请求共享该数量上限，分片并发不会直接乘出更多实际请求。该预算跨插件重载保留，旧请求结束才归还额度。
- 每片 4 MiB。共享缓冲额度允许最多 8 个分片请求体，先取得额度再组装，约 32 MiB 载荷加 multipart 封装。源文件、恢复副本和回读仍使用完整缓冲，此额度不等于总进程内存上限。
- 上传会话内，只重试失败片；已经确认的成功片保留。提交限流也复用当前会话。最多自动重试三次，尊重服务端完整等待时间；HTTP 限流或服务异常先设置共享等待，再放行后续请求。
- 网络写入结果不确定时先核验，不能确认则保留任务。暂停或超时后，尚未结束的原生分片请求仍占用请求与缓冲额度，等请求结束再返回任务；界面显示等待状态。
- 传输中心显示同时传输的分片编号、失败片等待倒计时及累计重试次数。全体分片等待时暂停速度与剩余时间估算；按实际确认字节计数，乱序完成与重试不会重复累加。
- 保留分片 MD5、整文件 SHA-256 和回读校验。上传进度达到 100% 后仍须校验并保存版本才算完成。

## 自动化与模拟对比

200 项自动化测试通过；另检查类型、生产构建、安装包内容及版本一致性。新增覆盖真实异步分片重叠、乱序完成、跨提供器共享额度、超时请求保留额度、发生不确定写入后停止派发新片、排队期间暂停、限流放行顺序、成功片不重传、提交复用会话和等待状态显示。授权取消测试改为等待请求真正开始后再取消，避免依赖固定微任务次数。

使用实际提供器代码与内存百度接口模拟器，给每片注入 **80 ms** 延迟，运行完整上传及回读 SHA-256 校验。请求预算 8，每片 4 MiB；只比较单文件分片并发 1 和 2。均校验一致，请求数量相同。

| 合成文件 | 轮数 | 分片数 / 总请求数 | 串行：上传阶段 / 整次处理 | 2 片并发：上传阶段 / 整次处理 |
| --- | --- | --- | --- | --- |
| 64 MiB | 各 3 轮，中位数 | 16 / 23 | 1.746 s / 3.229 s | 0.908 s / 2.422 s |
| 339 MiB | 各 1 轮 | 85 / 92 | 9.238 s / 17.280 s | 4.650 s / 12.928 s |

这说明注入的逐片等待可以重叠，**不代表真实百度网速或固定提速比例**。摘要计算和回读成本仍在。339 MiB 单轮受热身、分配器与运行顺序影响更大。

模拟器每 25 ms 采样进程 RSS：64 MiB 串行为 249–353 MiB、并发为 318–351 MiB；339 MiB 单轮为串行约 801 MiB、并发约 1443 MiB。模拟器会保留并复制源文件、分片、组装文件与回读数据，顺序运行也受内存分配器影响；这些数字不能当作 Obsidian 原生内存验收或单独归因于分片并发。仍需用户本机实测峰值与吞吐，不扩大现有大小限制。

复现：`node --expose-gc --experimental-strip-types scripts/benchmark-upload.mjs --mib 64 --rounds 3`，或 `--mib 339 --rounds 1`。报告保存在 `dist/upload-performance-<MiB>MiB.json`，不进入发布包。

## 本机验收与边界

重新启用插件，使用同一个允许传输的附件，分别设置分片并发 1 和 2，观察传输中心的分片、确认字节、回读阶段、失败等待及诊断统计。已存在的内容对象会被复用，不能把跳过上传的一轮当成吞吐对比。两轮须各自使用新内容才能比较实际上传；不要删除云端内部对象制造测试条件。

浏览器布局预览使用已安装 Obsidian 样式与合成数据，不访问账号或笔记。开发环境尚未完成 Windows/iPad 原生界面与真实百度吞吐验收。

电脑仍最高 512 MiB、移动端 20 MiB；大附件仍一次一个。不是流式 I/O，不提供跨重启的分片级续传，不永久清理云端对象，也没有减少独立完整性校验。

## English

Desktop **Upload slice concurrency** defaults to **2**, configurable from **1 to 4** under the transfer settings; mobile remains at 1. Existing file concurrency defaults to 8 (range 1–32), now also caps shared Baidu requests per vault across plugin reloads. A separate shared pool admits at most eight 4 MiB multipart payloads before allocation. Whole-file source and readback buffers remain; this is not a process-memory cap.

Failed slices retry within the current session, retaining acknowledged slices. Commit throttling reuses the same session. Up to three automatic retries respect the full server delay, with shared cooldown applied before admitting queued requests. Uncertain writes require verification. Native requests that outlive pause or timeout keep their request/body leases until they actually settle. The transfer center shows parallel slice numbers, retry countdowns and pending requests, without inventing bytes or declaring success before verification and version publication.

All 200 automated tests pass, with type/build/package checks. The table above uses the actual provider with an in-memory API simulator and an artificial **80 ms per-slice delay**, including full readback integrity verification. It demonstrates overlapping waits, not real Baidu throughput. RSS samples include mock copies and allocator effects (339 MiB: about 801 MiB serial vs 1443 MiB parallel in a single ordered run); they are not native memory certification. Real Windows/iPad throughput and memory checks remain pending.

Re-enable the plugin after installation. Compare slice concurrency 1 and 2 with distinct new file contents; deduplicated existing objects are not upload benchmarks. Desktop/mobile limits remain 512/20 MiB and one large attachment at a time. No streaming, cross-restart slice checkpoints or removal of integrity checks is included.
