# 自动同步与队列设计

状态：已在独立分支实现为 0.2.0 测试版本，自动化验证通过，真实设备验收待完成。日期：2026-10-15。实际功能及边界以 [0.2.0 说明](releases/0.2.0.md) 为准，下文保留设计依据。

## 目标与默认体验

开启自动同步后，保存文件会触发同步；本地没有改动时，也能发现其他设备发布的新版本。保留「立即同步」「预览」「暂停」入口，所有同步入口通过同一个调度器。

建议默认值：本地变动安静 2 秒后处理，连续变动最多合并 15 秒；远端每 60 秒检查一次，可配置 30–300 秒；检查间隔加入小幅随机延迟，降低两台设备同时请求的机会。执行中不再叠加远端轮询。文件传输继续使用已有并发设置，默认 8，保留大附件批次预算。

首次开启先核验连接、云端绑定、传输权限及未完成日志，再做一次完整对账。已有安装升级时新增自动同步开关，保留其原有设置；开启后的首次对账清楚显示可能上传、下载或保留冲突的情况。删除传播仍由已有的独立开关决定。

## 现状与需要修改的部分

- `src/main.ts`：按钮和命令直接启动任务；有插件级 busy，但忙时的新请求被拒绝，没有合并待办。前后台切换目前暂停并检查恢复日志。
- `src/sync/engine.ts`：有单任务互斥、三方比较、版本图、并发文件执行及恢复日志；当前每次计划都会读取并计算全部本地文件的 Hash。
- `src/sync/remote-vault.ts`：已有完整分页枚举、有效指纹对应的版本缓存及版本图校验。可以复用这些规则检查远端，不凭文件缺失推断删除。
- `src/platform/obsidian-adapters.ts`：已有设备及连接隔离的状态、恢复点和缓存目录，可增加隔离的调度状态；内部目录继续排除。

因此增加调度层，同时优化扫描入口；不能只给 `startSync()` 套一个定时器。

## 本地变动收集

监听 Vault 的 create、modify、rename、delete。普通文件、附件和外部编辑都以文件系统实际变动为准；目录事件标记需重新枚举路径。注册 create 监听时避免将 Obsidian 初始化时枚举的所有文件当成新建事件。

每条待办保存路径、变动序号、类型和最近变动时间。以路径合并重复编辑，不保存笔记正文。重命名记录新旧路径，目录移动触发子路径重新检查。通知只是「此处需要重新比较」，不能直接转成上传或删除命令。

同一文件连续修改只保留最新待办；上传开始后又修改时，运行中的版本继续按原日志处理，新修改留给下一轮。某轮结束时仅确认该轮捕获的变动序号，不能清空整个待办集合。

排除 Obsidian 配置、凭据、插件状态、暂存、缓存和恢复副本；冲突副本沿用当前排除策略。目录删除需要展开旧索引并检查删除开关。自动同步不自行开启删除传播。

## 统一队列

调度器保存一个合并后的待执行请求：触发原因集合、脏路径集合、远端需检查标记、是否需完整对账。多个事件不创建多个重复扫描任务。

队列状态：空闲 → 等待合并 → 检查变动 → 传输 → 空闲；另有等待重试、用户暂停、后台挂起、需要处理错误。界面显示具体原因。

同一 Vault 同时只有一个同步任务；该任务内部才按用户设置并发处理不同文件。手动「立即同步」跳过合并等待，任务执行中点击则合并为后续一次请求；不会启动第二个引擎。预览、恢复、配置导入与绑定变更同样参与互斥。

互斥需要覆盖插件重载：新实例不能与旧实例同时提交同一 Vault 的基线或日志。旧实例失效后停止派发新请求，保留未确认写入，后续实例先读取并核验恢复日志。

## 每轮执行

1. 捕获队列中的变动序号和当前设备、账号、应用、目录、远端库上下文。
2. 核验当前连接仍匹配；有未完成日志先恢复，遇到旧内容与新编辑冲突时暂停并保留待办。
3. 获取可信的远端版本清单。已有记录按新指纹复用；新记录或指纹变化时读取并验证。缺失摘要、分页失败、父版本缺失不能视为「远端没有变」。
4. 对本地变动及远端涉及的路径重新读取和计算 Hash；初次开启、重启、事件溢出、恢复前台或索引不可信时执行完整对账。
5. 使用现有基线与版本图生成计划。远端单独修改自动下载，本地单独修改自动上传；双方并发修改先保留所有有效内容，不按设备时间选赢家。
6. 按现有恢复日志、内容校验和串行本地提交规则执行。文件执行前仍重新验证依据。
7. 只确认成功覆盖且变动序号未更新的待办。执行期间到达的本地或远端变化触发下一轮，避免无休止的即时循环。

本地索引的时间与大小只用于减少候选范围，不作为内容一致或覆盖的依据。事件漏收由启动、前台恢复及低频完整对账补偿；建议完整对账间隔 10 分钟，可在性能验收后调整。

## 远端检查

首期采用前台定时检查，无需新增服务器。拆出只读取目录及版本元数据的入口；无变化时不下载笔记、不计算全部本地正文 Hash。

检查要覆盖完整设备目录和分页，新增设备也必须可发现。不能只比较本设备的最后一次操作，不能只用最大时间戳。服务端有效指纹与上次清单一致时结束；若有新记录、记录变动或清单不可信，再进入统一对账流程。

尽量把本次已验证快照交给紧随其后的规划，避免「轮询扫描一次、正式同步又立即扫描一次」。实际传输结束前仍按现有规则复查版本；无变化任务保留一次扫描的优化。后续时刻新出现的版本由后续检查发现。

轮询有请求成本，首期不承诺即时远端推送。应记录每次检查的请求数、缓存命中、耗时和失败/限流等待，以真实账号结果调整频率。

## 防止同步循环与重复版本

下载写入本地也会触发文件事件。不能简单忽略同步期间的全部事件，这会丢掉用户同时编辑的通知。记录插件已应用的路径、操作 ID 和目标 Hash，完成后重新核对；只有内容确实等于已应用版本时，才消除对应的待办。用户产生不同内容时继续入队。

队列仅表示重新检查意图；实际操作使用已有 journal 的操作 ID 重试。同内容不发布新记录。冲突分支及已生成的副本要复用，重复自动同步不能持续新增相同副本或记录。

## Git 式合并与冲突解决

现有实现具有父版本、不可变内容和多分支检测，但没有 Markdown 正文的三方自动合并。当前 `resolve()` 已能选择本地或一个远端内容、保存所有竞争版本，再发布引用全部已知冲突分支的新版本；入口位于传输预览。自动保留副本只是保护内容，不等于冲突已经解决。

下一步参照 Git 的共同祖先和三方合并模型：

- 一条版本链上连续修改，自动接收后继版本；相同内容不做重复传输。
- 同一文件有两个不同分支，且可取得唯一、已验证的共同祖先时，对「共同祖先 / 本地版本 / 远端版本」做三方文本合并。无重叠的文本变更可以合并；有重叠或无法确定的变更保留为冲突。
- 首期仅对大小、行数和运行耗时在验收范围内的 UTF-8 Markdown 开启自动合并。保留换行和编码约定，合并后检查可用的 Markdown/前置信息结构，但不承诺理解正文语义。过大文件、图片、PDF、缺少祖先、多个可用共同祖先、多个独立文件身份或三个以上竞争分支，先进入解决界面。
- 自动合并成功后也发布一个引用参与分支的新版本，并保留原始内容，不能只在本地改正文而不更新版本图。没有明确共同祖先时不靠时间或单次本地基线假造祖先。

设置页与状态区提供统一的「待解决冲突」入口，按文件展示：原路径、涉及设备、分支数量和变化摘要。时间仅用于说明。打开后查看共同祖先、各设备版本和可编辑的合并草稿；iPad 使用分栏切换与逐块操作，避免强制横向三列。

解决方式：

1. 采用一个完整版本。明确指出选中的设备与版本，所有其他内容仍保存在历史中。
2. 逐个冲突块采用本地、远端、两段都保留或手动编辑，预览完整结果。删除对修改、改名对改名使用专门选项，不能把删除当空字符串自动合并。
3. 明确选择「保留为两篇」时，为另一个版本生成可编辑名称的普通笔记，作为正常文件同步到其他设备；不能仅把它放进当前默认排除同步的冲突副本目录就声称两台设备都能看到。

未完成的合并草稿保存在本设备的内部状态中，暂停或重启后可继续；不会把未解决的标记写进正常笔记。界面用结构化冲突块跟踪完成状态，不因为用户正文中恰好出现类似标记的字符串而误判。

点击「确认解决并同步」后：重新验证当前本地 Hash 与远端所有分支；有新修改就保留草稿、刷新对比，不能覆盖新内容。验证通过后先保存恢复点、记录操作日志，上传并校验结果，再发布引用已解决全部分支的版本；本地应用完成后更新基线和冲突状态。其他设备收到该后继版本后自动收敛。如果发布期间又出现新的并发分支，按新冲突处理，不能把未知分支标成已解决。

队列按文件身份和涉及路径暂停冲突相关操作，其余独立文件继续同步。待解决项目稳定保存在收件箱中，不每轮弹窗、不重复生成相同副本，也不能仅因用户关闭窗口就标记解决。未知格式、损坏对象或不完整版本图仍按全局安全规则阻断相关任务。

合并测试至少包括：不同段落修改、同一行修改、相同改动、无共同祖先、多共同祖先、三端并发、删除对修改、改名冲突、图片/PDF、前置信息与换行、打开解决器期间继续编辑、确认时远端更新、合并记录已发布但本地未应用时崩溃，以及另一设备收到解决版本后不再重复报告原冲突。

## 离线、后台、失败与持久化

待办、重试时刻和上下文标识保存在设备及连接隔离的 Vault 本机存储；实际文件传输的阶段和内容仍由内部恢复日志管理。队列不存令牌或正文，不进入配对导出，诊断仅输出数量和状态，不输出路径。合并草稿单独保存在内部草稿目录。

离线时保留待办并延迟；系统 online 事件只是尝试重连的提示，不视为百度可达的证明。网络错误按递增间隔并加入随机延迟重试，尊重服务端 Retry-After；与接口内已有三次重试分工，避免内外重试相乘后持续打满请求。

授权失效、绑定变化、损坏对象、未知格式等错误停止自动派发并显示具体处理入口。用户点击暂停后保持暂停，网络恢复或轮询不得擅自启动；手动继续才恢复。

iPad 切到后台停止派发，当前原生请求可能仍完成或结果未知，不能显示为已撤回。回到前台后先核验日志、待办与当前内容，再根据自动同步开关继续。插件卸载取消监听与计时器，不承诺后台持续传输。

更换账号、应用或库后，旧队列保留在原上下文中并停止执行；新上下文重新对账。复制 Vault 时不得继承另一台设备的活动队列。配置导入不自动把另一设备的自动同步开关或队列带过来。

## 交付顺序与验收

第一步：实现可独立测试的调度器、持久待办及单任务入口，接入本地事件和设置开关。先验证突发 100 次修改合并、同一路径去重、任务中继续编辑、暂停/重启和忙时手动触发。

第二步：接入远端检查与快照复用。两端无本地变动时也能自动接收新版本；连续无变化检查不下载历史正文。所有分页、元数据缺失和校验错误继续阻断写入。

第三步：实现本地增量索引及自身写入核对，优化大量未修改文件的读取；覆盖目录移动、外部编辑、事件漏收、导入批量附件和索引损坏回退。

第四步：补齐统一冲突入口、草稿、确认发布与两端收敛，再加入有明确共同祖先的 Markdown 三方合并。没有正文自动合并能力时，界面必须明确展示当前保留或选择完整版本的能力边界。

第五步：真实 Windows/iPad 双端验收后再扩大发布。必测离线双方编辑、同步时继续输入、修改对删除、连续前后台切换、限流、写入结果未知、插件重载及账号切换。记录模拟结果和真实设备结果，不互相替代。

发布时测试分支与社区安装目标需要真正分离，不能仅依赖 GitHub prerelease 标记。自动同步首版可作为 0.2.x 功能交付，现有手动入口保留。
