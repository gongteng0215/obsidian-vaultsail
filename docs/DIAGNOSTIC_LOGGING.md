# 排错日志设计与实施 / Diagnostic logging

状态：0.2.15 本地预览实现。当前社区发布版本与本机预览版本分开管理；本文不表示 0.2.15 已发布到社区。

0.2.18 补充：目录列表及文件元数据请求只增加 `digestsStandard`、`digestsOpaque`、`digestsMissing`、`digestsRejected` 四类数字计数，用于排查指纹未识别导致的反复下载。它们统计标准摘要、32 位不透明摘要、缺失字段与格式异常，不记录摘要原值、路径或响应正文。

## 要解决的问题

过去的同步记录只保存 `unknown` 等摘要，异常转换成中文提示时又丢掉了底层异常，导致截图不能回答「哪个操作、哪个请求、失败前保存到了哪一步」。这套记录器保留错误原因链和结构化上下文，同时维持原有同步、重试和恢复判断。

旧版本未记录的异常无法补录。这套机制从启用新版后开始收集，不读取旧笔记正文来猜测原因，也不会为了诊断重放上传、删除或恢复任务。

## 三层记录及关联

| 层 | 记录内容 | 排查作用 |
| --- | --- | --- |
| 任务时间线 | 会话、任务编号、序号、时间、手动/自动、同步方向、阶段、扫描数量、队列来源及当时的并发/大小/删除设置 | 还原触发条件、阶段顺序及配置 |
| 操作结果 | 请求类别、请求编号、HTTP 状态、百度数字错误码和数字请求 ID；本机读写步骤、匿名源/目标、长度、字节数和类型；上传分片里程碑与重试等待 | 区分授权、网络、服务端、本机文件系统与并发问题 |
| 错误详情 | 诊断编号、异常类别、白名单错误码、系统 errno/syscall、重试属性、最多四层原因、每层最多八个调用位置、匿名错误签名 | 保留底层证据并定位对应源码 |

`session` 区分插件加载；`taskId` 关联整轮操作；`historyId` 对应本机同步历史；`requestId` 对应一次实际网络调用；`fileRef` 关联同一文件；`operationRef` 关联一次恢复/发布操作。逐文件失败还将 `diagnosticId` 写入同步历史，并显示在传输中心和同步记录中。

每个事件保存插件版本、Obsidian API 版本、桌面/移动分类及构建编号，历史记录不因升级混淆所属代码。相同毫秒内用会话内递增序号排序，不能靠随机 UUID 推断事件先后。

网络调用开始时捕获任务上下文。即使原生请求在超时后、下一轮任务开始后才返回，结束记录仍属于原任务，不会被记到新任务中。预期中的设备授权 `authorization_pending` 不当作失败。

## 捕获范围

- `run()`、手动预览执行、同步、恢复与冲突处理任务。
- 同步引擎逐文件失败；排队但未执行的文件不额外伪造一次实际失败。
- 百度实际请求的开始、返回或原生异常，以及现有重试等待回调。
- 本机目录、暂存、恢复副本、状态提交、笔记和附件应用操作。
- 恢复日志成功保存后的 `prepared / published / applied` 阶段；尚未确认的写入仍按原恢复机制核验。
- 同步历史保存/读取失败、缓存损坏/保存失败、队列恢复/保存失败。
- 设备配对阶段、密钥存储访问和配置保存异常。

不安装收集整个应用异常的全局钩子，不采集其他插件的错误。初始化完成之前的异常、插件强制退出后才发生的异常，以及没有经过这些入口的第三方行为，不在本轮覆盖保证中。

## 本机保存策略

实际目录：`<Vault>/.vaultsail-state/<本设备 ID>/diagnostics/`。属于插件内部排除目录，不参与同步、配对导出或正文扫描。

- 常规事件合并后约两秒异步保存，失败事件与任务结束尽力立即触发保存。
- 每批最多 24 条；每段上限 128 KiB，文件写入后先校验再提交。
- 失败批次与常规批次分别轮转，各最多 16 段；合计最多 32 段、约 4 MiB。常规检查不挤掉失败分区。
- 最多保留七天；容量先达到时按各分区最旧记录淘汰。这是上限，不承诺完整保留七天的所有事件。
- 轮转只处理严格匹配本插件命名规则的文件，不触及笔记、同步基线、恢复副本或其他文件。
- `.next` 提交中断后可在读取时恢复可用记录；重复保存同一批次会核对内容。
- 同步历史与诊断记录使用不同的写入队列；诊断写入不持有同步任务锁。
- 写盘失败不抛回同步流程；内存最多保留 1,000 条，待写缓冲最多 512 条，超出会计数。稍后事件、任务结束或导出会再次尝试保存。
- 存储失败、不可读取的段、缓冲丢弃及导出截断会明确显示。记录器自身写入失败不递归写另一条失败日志。
- 强制终止进程时，未落盘的尾部事件可能丢失；不承诺关机或强杀下零丢失。

记录分片状态改变、已确认分片数、尝试次数等里程碑，不记录每个字节或重复心跳。单个分片内的实时吞吐仍受现有网络接口能力限制。

## 详细与脱敏的边界

详细指可用于关联、定位和复现的结构化证据，不是保存所有请求或直接复制原生异常。

| 可以记录 | 不记录 |
| --- | --- |
| 固定步骤、HTTP/百度/系统错误码、errno、白名单 syscall | 密钥、令牌、授权码、设备验证码、配对码和密码 |
| 本机匿名文件标识、类型、长度、目录深度、字节大小 | 原始文件名、本机绝对路径、云端路径、账号或库名称 |
| SHA-256 加盐后的错误消息签名 | 原始异常消息、原始堆栈字符串、任意函数名 |
| 源码所属分类和行列位置 | 请求 URL、下载链接、请求头/正文、接口响应正文、笔记正文 |
| 数字百度请求 ID、任务设置与阶段 | 用户配置文件、密钥引用、恢复副本内容或草稿内容 |

匿名标识使用当前设备保存在 Vault 本地存储中的随机盐。同设备重启后可关联，盐不进入报告；另一个设备的匿名文件标识通常不同。完整文件路径仍可由用户在本机同步历史中，通过诊断编号对照。没有采用「先保存原文，导出时再尝试替换」的方式。

写入与导出均重新按白名单重建对象。即使日志被加入了额外 `body`、`url`、`token` 等字段，也不会随标准报告导出。未知原生错误至少保留异常类别、调用位置和匿名签名；新增可信错误码时可以扩展白名单。

## 用户操作

1. 启用 0.2.15 或更新版本；记录自动开始，无需填写开发者账号或打开控制台。
2. 报错时保留诊断编号，进入「传输与恢复 → 诊断与报告 → 查看与导出排错日志」。也可通过命令面板打开。
3. 按诊断编号或任务编号筛选最近失败，展开查看安全详情。
4. 选择「导出日志文件」。生成 `VaultSail-配置/vaultsail-diagnostics-<随机编号>.json`，导出目录已排除同步；也可复制报告。
5. 反馈时附上报告、诊断编号、设备及 Obsidian 版本，并描述「做了什么、预期什么、实际什么、另一设备是否同时修改」。仍不要提供配对码、SecretKey 或 `data.json`。

报告包含保留范围内最多 2,000 条去重事件，并设 8 MiB 导出上限。达到上限时删除部分旧事件并报告截断数量。导出内容只写本机；没有自动上传、遥测或第三方错误平台。

读取和导出异步执行。弹窗关闭后忽略迟到结果；没有定时重建设置页或抢回滚动位置。读取时复制/导出按钮暂停，避免无反馈或导出尚未就绪的内容。

## 开发者复现流程

1. 用诊断编号找到根失败，按 `taskId` 汇集事件，结合 `historyId` 与匿名文件/操作标识确认同一轮行为。
2. 检查构建、平台、大小、并发、删除开关、增量/完整检查，以及远端请求和本机提交的顺序。
3. 区分实际原生失败、HTTP/百度业务失败、服务端限流、逻辑超时、迟到响应、校验失败与本机记录故障。
4. 检查恢复检查点：内容准备、日志已保存、记录已发布或本地已应用；保持原日志，根据实际结果恢复，不能简单重放所有写入。
5. 用相同文件类型、大小、路径长度/深度和并发在隔离测试库构造场景。需要实际内容才能复现时，应另行确认范围，不能从日志猜测内容。
6. 添加故障注入回归，再修正代码；不把隐藏提示改成无限重试或跳过校验。

每次生产构建在本机保存 `dist/debug/<buildId>/`，包含实际主文件、独立源码映射、版本和 SHA-256 元数据；正式插件 ZIP 仍只有三个插件文件。源码映射不安装到用户 Vault，也不进入诊断报告。

```powershell
node scripts/resolve-diagnostic-stack.mjs report.json dist/debug/<buildId> resolved.json
```

该工具核对构建编号、主文件和映射 Hash 后，将属于该构建的插件调用位置转换成源码文件及行列；其他构建的记录跳过。原报告不会被覆盖。构建编号是提交 SHA；本机未提交构建附带 dirty 标记。源码归档不含 Git 时使用来源标识，不能将其冒称为已发布提交。

## 本轮验证与后续

自动化覆盖：原因链与循环原因、原生文件错误、消息/堆栈/请求中的敏感样本、日志篡改、迟到请求关联、OAuth 等待、重启读取、提交中断、幂等保存、轮转/期限/范围、损坏及超限文件、磁盘失败与内存上限、历史诊断编号、普通检查不淘汰失败分区、源码映射 Hash 和构建匹配，以及设置页打开与文件导出。

自动化使用隔离适配器和故障注入，不替代真实 Obsidian/iPad 存储验收。下一次真实失败应先验证「提示编号 → 本机记录 → 导出 → 还原调用位置」链路，再根据记录添加新的现场回归。后续可增加跨报告错误分组、按任务浏览时间线和更多已证实的系统错误分类；不默认引入远程收集服务。

## English summary

Version 0.2.15 adds local structured diagnostics: correlated sessions/tasks/requests/files, numeric settings, native and API failures, bounded cause chains and stack positions, upload milestones and verified recovery checkpoints. Raw messages, paths, credentials, note contents, URLs and request/response bodies are never persisted. Failed and routine segments have independent bounded retention. Logging failures remain advisory, with an explicit bounded in-memory fallback. Reports are exported only on user action; build-matched source maps remain in the developer build archive. Earlier unrecorded failures cannot be reconstructed retroactively.
