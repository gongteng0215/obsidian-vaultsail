# VaultSail 大文件同步实施方案

[English](LARGE_FILES.md) | **简体中文** · [版本规划](ROADMAP.zh-CN.md) · [当前功能](../README.zh-CN.md#完整功能清单)

> 当前进度（2026-10-20）：本文下方为以 0.2.0 为基线的历史设计。当前 0.2.22 本地预览已支持电脑 512 MiB（20–512 可配）、移动端 20 MiB、按需分片与电脑默认 2 片并发；仍为整文件缓冲，没有流式 I/O 或跨重启分片续传。当前能力以 README 和最新发布说明为准。

日期：**2026-10-16**。设计基线：**0.2.0**。进度：**L0 本地预检、跳过处理与按需分片已有 0.2.1 预览试作**，见 [验证与边界](releases/0.2.1.md)；其余阶段仍是设计，尚未实现。本版不提高 20 MiB 上限、不迁移云端格式，真实设备验收待完成。下文版本归属为条件目标，不是发布日期或支持上限承诺。

## 1. 建议与目标

采用“先隔离超限文件 → 减少内存复制 → 验证各平台能力 → 有限放宽 → 真正分块与可恢复传输”的顺序。普通笔记优先，大附件可暂停、可恢复，不能让一个超限附件阻断其他正常文件。

首要用户场景是较大的 PDF、扫描件和图片。视频、磁盘镜像、超大压缩包暂以外部网盘链接使用，不承诺 GB 级跨端同步。

成功标准：

- 不再因为一个已识别但超出本机能力的文件，使整库普通文件不能同步。
- 文件并发上限仍由用户配置，默认 8；大文件另受内存和请求预算控制，首期同时仅 1 个。
- 传输源在操作中稳定；正文、暂存、恢复与版本记录保持一致。
- 只有验证完成的内容才成为有效版本或替换本地原件。
- 真正流式路径的受控缓冲不随文件总大小线性增长；整文件路径必须如实标为“完整缓冲”。
- 账号、应用、目录或库变化后，旧任务不在新上下文执行；配对不迁移队列、临时 URL 或断点。

## 2. 当前实现与不能直接调大数字的原因

以下来自当前代码核对：

| 位置 | 当前行为 | 需要改变的部分 |
| --- | --- | --- |
| `src/core/safety.ts` | `MAX_FILE_SIZE = 20 MiB`，`checkSize()` 多处复用 | 拆分逻辑大小、正文缓冲和元数据限制 |
| `src/platform/obsidian-adapters.ts` | 本地读取返回完整 `ArrayBuffer`；暂存、恢复和应用后校验会重读内容 | 元数据先行，增加快照/分块能力，避免隐式整文件回退 |
| `src/providers/baidu-provider.ts` | 已按 4 MiB 上传分片，但先用 `slice()` 复制所有分片，还会构造 multipart 请求体 | 分片按需生成、用完释放，不能只改上传循环 |
| `src/platform/obsidian-adapters.ts`、`src/providers/http.ts` | 网络传输最终返回完整 `response.arrayBuffer` | 大下载需要有界且可取消的传输适配器 |
| `src/core/concurrency.ts` | 默认并发 8、用户范围 1–32，批次逻辑大小约 24 MiB | 24 MiB 是逻辑数据预算，不是进程内存硬上限 |
| `src/sync/engine.ts` | 扫描逐文件读取并 Hash；执行保留暂存/恢复内容 | 超限必须在读正文前判断，恢复与冲突路径也需要分块能力 |
| `src/sync/remote-vault.ts` | 远端版本声明的逻辑大小也经过 `checkSize()` | 大文件记录会让旧 0.2.0 客户端扫描失败，需读端兼容先行 |

当前“分片上传”不等于“低内存流式同步”，也不等于“重启后断点续传”。上传、下载、Hash、快照、冲突保留和应用后校验都必须纳入设计。

## 3. 分阶段交付与版本关系

| 阶段 | 条件版本目标 | 交付 | 开放边界 |
| --- | --- | --- | --- |
| L0 | 0.2.x 稳定性后续补丁 | 元数据先行、超限条目、部分完成状态、小文件继续、分片按需复制 | 上限仍为 20 MiB，不发布大文件记录 |
| L1 | 0.3.x 平台验证阶段 | 桌面/iPad 能力原型、读端识别与本机策略分离、内存/磁盘基准 | 只做受控测试，先让各端能识别记录 |
| L2 | 0.4.x 性能阶段，通过 L1 后 | 已验收平台可配置附件上限，单大文件、有预算的完整缓冲路径 | 默认仍 20 MiB，超过部分显式开启，未验收平台保留原限 |
| L3 | 0.4.x 后续或独立预览，通过能力门槛后 | 桌面分块快照、上传、下载、增量 Hash 与持久恢复 | 先桌面；iPad 只有独立通过门槛才开放 |
| L4 | 0.5.x 恢复体验或以后 | 断点管理、磁盘占用、重试/清理预览、双端一致体验 | 接入历史恢复，不自动永久清理云端 |

L2 若完整缓冲实测不可靠，可以跳过“提高上限”，直接等待 L3；不能为了按版本交付而开放危险配置。主线仍先完成 0.2.1 稳定性。移动端不因桌面验收通过就自动解锁。

## 4. 设置与用户流程

### 设置项

| 项目 | 初始策略 | 校验 |
| --- | --- | --- |
| 本机单文件传输上限 | 保持 20 MiB，后续提供经过验收的档位 | 整数、范围、平台与引擎能力共同约束；无“无限制” |
| 大附件并发 | 首期固定 1 | 与总文件并发共同生效，不额外叠加 8 个大文件 |
| 大附件自动同步 | 新增能力首期默认关闭 | 用户可先查看清单并手动允许，验证后再开启 |
| 大附件分界 | 初期沿用 20 MiB 作为调度分类，和允许上限分开 | 不是服务商分片大小，也不是 Markdown 合并预算 |
| 本机受控内存预算 | 根据平台实测确定，首期不开放任意数值 | 预算不足则等待或标记不支持，不临时突破预算 |
| 缓存/暂存占用 | 展示当前任务与可安全清理的数据 | 活动日志、有效草稿和唯一恢复内容不能清理 |

可以用 50、100、200 MiB 作为测试候选大小；这些是测试点，不是本方案已批准的配置档位。最终允许值由设备与路径实测决定，不按设备名猜测可用内存。

现有“同时传输的文件数”继续是总上限，最大 32、默认 8，保留已有选择。新偏好只在当前设备生效，不随配对隐式迁移；修改设置不自动解除账号和库绑定。

### 日常操作

1. 用户点击同步或文件事件入队。
2. 先扫描大小与能力，再生成小文件动作和“大附件等待/超限/未启用”的清单。
3. 小文件优先处理，大附件等待单独名额；用户可查看原因、手动传输、延后或打开所在位置。
4. 结果显示“完成 N，跳过 M，需要处理 K”，不会有跳过项却只写“全部完成”。
5. 跳过项保留在独立的受阻清单，不无限高速重试。文件变更、上限/能力变化或手动重试时重新评估；周期检查保留可见状态。

初期不自动把附件改成外链，不替换 Markdown 链接，不生成看似真实附件的占位文件。

## 5. 架构与接口调整

```text
文件事件/手动同步
        ↓
元数据清单 → 能力与策略判定 → 超限/受阻清单
        ↓ 可传输文件
公平调度器（总并发 + 单大文件 + 内存额度）
        ↓
稳定快照 → 增量 Hash → 可恢复传输 → 完整校验
        ↓
不可变内容/版本发布 或 本地恢复保护/最终应用
        ↓
基线与任务日志提交
```

建议新增的接口职责，名称可在实施时调整：

| 接口 | 职责 | 不能承担的假设 |
| --- | --- | --- |
| `LocalFileIO.stat()` | 大小、类型和本地变动线索，不读正文 | mtime/size 相同不代表内容相同 |
| `LocalSnapshot` | 操作范围内稳定的暂存源，描述符、大小、Hash、分块读取 | 不能把持续变化的原文件当已冻结快照 |
| `TransferCapabilities` | 明确上传/下载/Hash/快照/恢复/提交各自是否有界 | 不用单一 `streaming=true` 掩盖某环节整文件分配 |
| `BinarySource` / `BinarySink` | 按 offset 读取、写入/顺序追加、完成与关闭 | 方法返回小块不代表底层没有先读全文件 |
| `TransferBudget` | 在申请缓冲或请求前预留额度，结束后释放 | 文件数上限不能替代字节预算 |
| `ResumableTransfer` | 会话、分片结果、远端核验与恢复 | 本机已发送不代表服务端确认 |
| `LargeFileJournal` | 设备/库/账号范围、快照、对象身份与阶段 | 不保存凭据、下载链接或正文 |
| `BlockedFile` | 超限、未启用、缺能力、磁盘不足等用户可处理状态 | 不能将缺失父版本/损坏对象降级成普通跳过 |

保留小文件现有接口作为有上限的兼容适配器。大文件路径禁止偷偷调用旧 `read()` / `blob()` 返回完整缓冲；同样检查冲突保存、恢复点、文件替换和最终验证。

## 6. 扫描、跳过与基线的正确性

必须区分以下状态，不能只用 `Map<path, hash>` 表达所有本地情况：

| 状态 | 含义 | 允许推断删除吗 |
| --- | --- | --- |
| `missing` | 完整枚举确认不存在，且有可信基线 | 仍需明确删除规则和开关 |
| `present-readable` | 存在且本轮可校验 | 按正常版本比较 |
| `present-blocked` | 存在，但超限、禁用或缺少能力，Hash 未更新 | **不允许** |
| `unknown` | 枚举/读取失败或结果不完整 | **不允许，阻断相关写入** |

具体规则：

- 所有路径先做安全与碰撞校验，之后根据 `stat` 判断是否读取。可识别的超限文件仍算“存在”。
- 跳过本地大文件不删除它的基线、不标记远端删除、不发布无内容的版本。
- 远端合法大文件可进入版本图，但本机不支持时冻结该文件/身份及关联重命名路径的应用与基线，继续独立文件。
- 远端记录“已发现”与内容“已验证应用”分开；不能因记录已缓存就把未下载大文件算完成。
- 删除、旧路径退役、身份冲突均要看关联受阻状态，防止大文件被遗漏后触发间接删除。
- 队列不要把跳过当作文件已传输；也不要把同一受阻文件每 2 秒重新塞回运行队列。
- 不完整分页、未知格式、父版本缺失、记录改写、路径越界仍属于安全错误，不能为“继续其他文件”而忽略。

## 7. 内存、磁盘和调度

### 内存预算

先修复所有分片提前复制：只为当前需要的分片生成请求体，MD5 列表可逐块计算后仅保留摘要。`subarray()` 只创建视图，但会延长原缓冲寿命，不能当释放原文件。

完整缓冲模式的估算必须包含源文件、现有目标文件、下载/回读响应、请求体、解码与 Hash 临时对象，以及待串行提交而仍存活的完成任务。初步用保守系数建模，再以实测校准，不宣称 `24 MiB 批次 = 24 MiB RSS`。

分块模式的受控部分可写成：

```text
受控缓冲 ≈ 在途分片数 ×（读取块 + 请求体 + 响应块）
          + 摘要/日志开销 + 完成但尚未提交的缓冲 + 安全余量
```

在申请正文、分片和网络响应之前获取预算额度，持有到最后消费者释放；不能仅在上传调用返回时释放。流式设计目标是随分片并发增长，而不随整个文件大小增长。JS 垃圾回收、原生网络缓存和操作系统占用仍需真实内存测量，软件计数不能构成进程内存硬上限。

初期单大文件、分片顺序发送；分片大小沿用当前百度适配器的 4 MiB 作为原型参数，实际以应用/API 能力验证为准，不能把 SDK 的能力当本应用已获准。

### 调度公平性

- 优先可快速完成的小文件，但大文件等待超过一个调度窗口后获得机会，避免持续编辑导致永久饿死。
- 大任务按可验证分片边界让出调度机会，当前原生请求未结束时不声称已经取消。
- 总请求并发、元数据请求和分片请求统一计算，不能“8 文件 × 每文件 8 分片”失控。
- 同文件继续修改创建后续待办，运行中的快照与操作 ID 不复用给新内容；旧版本可以保留，但不能把它标为当前本地内容已同步。
- 限流降低派发，尊重服务端等待；结果未知的写入先核验，不能同时开启新一轮重试。

当前引擎会先处理全局未完成日志，因此仅增加“小文件优先”排序不够。L3 需要按文件身份及新旧路径持有传输租约，在已持久化检查点让出后，允许独立文件进入同一个协调器；共享状态仍串行提交，同文件和关联改名不能绕过租约。安全错误仍可阻断全局。实现前要重测现有“有日志先恢复”规则，不能直接删掉保护。

超时的 Promise 不代表底层请求已结束。预算、任务互斥和在途计数要等待原生操作实际完成或已确认中止，插件重载后也不能丢失这些约束；无法做到有界取消的传输器不进入大文件支持档位。

### 磁盘预算

预估包括上传快照、下载暂存、目标旧版恢复、崩溃后尚未清理数据。不能只检查附件本身大小。可获得可靠空闲空间时预检，否则展示估算，写入失败后保留有效原件和可恢复状态。

暂存必须位于插件拥有的隔离目录，路径由验证过的 ID 构建。不能把 `.vaultsail-state/` 或系统临时目录中的任意文件认作可清理对象。

## 8. 稳定快照与上传流程

1. 捕获当前本地与远端版本依据，记录账号、应用、目录、库和设备上下文。
2. 从源文件创建本机不可变快照，分块写入暂存并计算整文件 SHA-256 和服务端要求的块摘要。
3. 创建快照期间监控变动序号及前后文件状态；发现变化、短读或源身份变化就丢弃未确认快照并重排。mtime/size 只能作为变化线索，不能取代内容校验。
4. 非流式能力下只在已批准上限内创建完整缓冲快照。缺少可靠快照/并发写保护的移动路径不得宣称支持大文件。
5. 快照稳定后确定 `blobs/<整文件SHA256>`，写恢复日志，再申请上传会话。整文件对象路径需要 Hash，不能在尚未确定内容时先随意发布。
6. 按服务端要求的分片顺序/索引上传，每次验证响应摘要，再保存已确认进度。MD5 仅用于百度分片协议，最终内容身份仍是 SHA-256。
7. 分片完成后提交文件，核对对象路径、大小和身份。提交响应丢失时先检查最终对象，不能直接再创建一份。
8. 使用有界下载读回校验整文件 SHA-256；已有完整验证缓存只有在新鲜元数据证明同一对象时才可复用。
9. 内容确认后，才发布不可变操作记录。操作 ID 在该快照重试期间固定。
10. 发布前后重新核验版本依据。出现新远端分支则保留分支，不能用快照无条件覆盖。源文件继续编辑则保留新待办，并在日志中区分“快照已发布”和“当前本地仍有更新”。

平台没有跨其他程序的可靠读锁时，不承诺对任意外部并发写入提供绝对原子快照。必须原型验证可用的快照/锁定策略；否则限定该平台大文件为稳定文件的手动流程，并在最终核验发现变化时停止。

## 9. 下载、Range 与本地应用

1. 读取有效版本、对象身份、总大小与预期 SHA-256，捕获本地目标依据。
2. 从受允许的官方主机取得短期下载链接，令牌/URL 仅在内存使用。刷新令牌或链接后重新核对对象身份。
3. 只有实际支持有界响应、取消和范围校验的传输器才进入分块下载；普通 `requestUrl` 返回完整 `ArrayBuffer` 不能直接当作无限大文件流。
4. 范围请求必须核对 `206`、`Content-Range` 起止/总长、实际长度和同一对象身份；处理 `416`、截断、压缩表示差异和链接过期。不凭 `Accept-Ranges` 一项认定可用。
5. 若服务端忽略 Range 返回 `200`，只有可提前停止的流式通道可在预算内中止；完整缓冲通道可能在检查状态前已经读完整文件，因此不能给大文件使用这种“事后检查”兜底。
6. 有强验证器才使用适用的条件范围请求；不能把任意百度 MD5 或弱 ETag 直接拼成 HTTP `If-Range`。没有可靠对象一致性时重新开始，最后全量 SHA-256 必须通过。
7. 下载按已确认的连续边界写入暂存。重启后重读并校验已有暂存前缀，不仅相信长度/位图；不直接持久化易变的 Hash 库内部状态作为恢复依据。
8. 完整暂存 Hash 与大小符合预期后，才准备应用；先验证目标未变并创建经过验证的恢复副本。
9. 在平台已验证的提交协议下，用完整暂存替换目标，并确认 Obsidian 的索引、事件、缓存同步。不能只用底层文件改名就假定界面和文件系统都已一致。
10. 应用后再次验证内容，最后推进基线并完成日志；任何阶段崩溃都能区分旧文件、暂存和新结果。

“备份后写入”不是所有平台上的原子 compare-and-swap。必须测试最后核验与替换之间的并发编辑窗口；没有可靠保证时，不允许自动替换大文件，改为受控手动完成流程或继续标为不支持。Hash 不一致不能仅显示警告后继续推进基线。

## 10. 断点与恢复日志

在当前操作日志之外，增加经过迁移的传输日志；恢复日志仍在本机，不进入云端操作记录或配对导出。

| 字段组 | 保存内容 |
| --- | --- |
| 归属 | 日志版本、设备/库/连接指纹、操作 ID、方向、文件身份 |
| 源依据 | 相对路径、快照 ID、逻辑大小、整文件 SHA-256、期望本地 Hash、父版本 |
| 上传会话 | 受保护会话引用、分片大小、摘要和服务端确认状态；不将原始会话能力放入普通日志 |
| 下载断点 | 暂存 ID、已验证连续长度、对象身份与分段校验信息 |
| 提交阶段 | 快照已准备、内容传输中、最终对象待核验、内容已核验、记录已发布、本地应用中、基线已提交 |
| 调度 | 安全错误分类、重试时刻、暂停原因，不存凭据或正文 |

`uploadId` 属于会话能力信息，优先 SecretStorage 或受保护的本机会话项；若平台无法安全保存，则重启后放弃该会话并重新申请，不把它加入普通诊断。日志不能保存 access/refresh token、App Secret、下载签名 URL、请求头或正文。

恢复顺序：

1. 验证归属、日志格式、暂存 Hash 与当前绑定；上下文不符则停止原任务。
2. 上传位图仅表示本机收到过确认，不证明服务端现在仍保留分片。必须按应用真实支持的官方接口核验；不假设存在可用的分片查询接口。
3. 若会话可安全恢复则继续缺失片；会话失效或无法确认时，用同一快照和原操作 ID 新建上传会话。旧未提交片不成为有效笔记。
4. 结果未知的最终提交/记录发布先读取核验。远端已存在且内容相同就继续下一阶段，内容不同则完整性错误。
5. 本地应用中断时先核对旧/新/暂存指纹和恢复点，不能盲目重复替换。
6. 用户结束旧任务只结束重试，保留可恢复内容；清理须单独预览，未完成操作不得被自动淘汰。

日志写入采用可恢复的临时文件与替换协议，串行提交。旧插件不认识新日志时不能假装降级安全；升级前保留状态，降级前必须完成或明确结束相关任务并使用受支持的恢复步骤。

## 11. 云端格式与旧客户端兼容

首选保留 `vault.json + blobs/<整文件SHA256> + ops`，百度上传分片只属于传输层，不在首期增加新的云端“分块清单”格式，也不将分片数乘到操作记录数上。

**关键事实：0.2.0 会拒绝逻辑大小超过 20 MiB 的版本记录。** 即使保持 schema 1，一台新设备上传大文件后，旧设备仍可能停止整个扫描。因此不能把“schema 没变”描述为“所有旧设备兼容”。

实施顺序：

1. 将“逻辑大小合法性”“本机传输策略”“元数据对象大小”拆开。逻辑字段需安全整数、非负、协议固定上界；不得依赖用户当前设置判断远端记录是否合法。
2. 先发布兼容读端：认识已支持格式的大文件描述，能标出本机受阻而继续独立小文件；此时不启用超限写入。
3. 协议固定上界、元数据文件上限、记录数/父版本数限制保持独立，禁止因放宽附件而放宽 JSON 或日志安全边界。
4. 大文件写入设置明确提示：所有参与设备需要兼容读端，包括离线设备。历史设备列表不能证明全部客户端已升级。
5. 已有库启用需用户明确选择；无法确认兼容时，保持关闭，或为新能力创建独立云端库。不能自动迁移原库或向未知旧客户端推送新记录。
6. 不通过删除大文件操作或改写不可变历史来实现回退；一旦发布过大文件历史，简单删除当前附件也不能让旧解析器重新兼容。

若原型最终需要云端 chunk manifest、内容分块格式或新的提交语义，应另起 schema 迁移设计，不在这次优化中悄悄变更。大文件上限、自动同步偏好不自动随账号配对导入。

## 12. 电脑与 iPad 的能力门槛

| 能力 | 桌面原型 | iPad 原型 | 不通过时 |
| --- | --- | --- | --- |
| 读取 | 限于当前 Vault 的桌面文件分块接口，验证路径和文件身份 | 验证公开接口/受支持资源通道能否真的分块，不能引用桌面 Node API | 保留完整缓冲上限 |
| 暂存/恢复 | 分块写入、复制与校验，验证索引同步 | 验证分块写入、追加、重启及后台中断行为 | 不开放大文件自动应用 |
| 网络 | 可取消的有界上传/下载与 Range 处理 | 官方主机、CORS/重定向、请求挂起与取消逐项验证 | 无能力则明确不支持，不回退整文件 |
| 最终提交 | 验证可恢复替换及并发编辑窗口 | 验证 Vault 索引、原生文件与事件一致性 | 手动受控流程或继续受限 |
| 测量 | JS、原生进程内存、磁盘与请求统计 | 真机稳定性及可获得的进程内存证据 | 不宣称已证明内存有界 |

Obsidian 官方类型定义中的常用二进制读取返回 `ArrayBuffer`；`appendBinary` 标注自 **1.12.3** 提供，而当前插件最低为 **1.11.4**。因此不能无条件调用追加接口后仍宣称兼容所有最低版本。[官方 API](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)

L0 保持当前最低版本；后续若依赖新 API，要么按功能检查并禁用不支持的路径，要么在相应版本明确提高最低 Obsidian 版本并更新 `manifest.json` / `versions.json`，不能静默降级。

## 13. 错误与进度

需要区分：等待大文件名额、受内存预算限制、磁盘不足、文件超限、平台缺能力、兼容设备未确认、网络退避、会话过期、源文件变化、对象身份变化、校验失败、应用待恢复。

进度至少拆为“已发送/已接收字节”“已验证字节”“已完成文件”，预计算、传输、回读校验和最终应用分别显示；不能因上传结束就宣布整文件已完成。

普通超限是受阻状态，不伪装成网络异常；完整性失败仍停止相关写入。若原始异常可能包含签名 URL 或凭据，只输出固定安全分类和步骤，不直接展示原始响应。

## 14. 测试与验收矩阵

自动化使用可控源、可控网络与故障注入；大文件测试数据按块生成，不先一次分配整个测试文件来证明“低内存”。真实测试使用隔离目录和非私密样本。

| 类别 | 必测内容 | 通过标准 |
| --- | --- | --- |
| 大小边界 | 0 B、块边界前后、20 MiB 前后、50/100/200 MiB 候选 | 策略准确，支持范围内 Hash 一致，未支持项明确受阻 |
| 混合队列 | 100 个小文件加多个超限/大附件，期间持续编辑 | 小文件继续，大文件有公平机会，待办不丢、不高频重试 |
| 扫描语义 | 超限已存在、远端超本机限、重命名关联、排除和枚举失败 | 不把受阻或未知当缺失，不误删、不推进假基线 |
| 内存 | 文件规模增大、总并发 1/8/32、请求/完成队列堆积 | 有界路径无文件大小线性驻留，完整缓冲路径符合已验收上限 |
| 上传恢复 | 每片前后、会话过期、提交响应丢失、记录发布前后 | 核验真实结果，无重复有效操作、无未验证版本 |
| 下载恢复 | `206/200/416`、截断、错位范围、对象变化、URL 过期 | 不拼接不同对象，不整文件隐式回退，最终 SHA-256 正确 |
| 本地安全 | 快照时编辑、最后替换时编辑、磁盘满、写失败、重启 | 原件/恢复点可保留或恢复，新修改不被静默吞掉 |
| 冲突/历史 | PDF 双端修改、保留两篇、云端旧版恢复 | 不做二进制文本合并，不整文件隐藏分配，分支可恢复 |
| 兼容 | 旧 0.2.0、兼容读端、受限 iPad、已启用大文件库 | 真实记录兼容行为，不声称旧端自动跳过；迁移有预检 |
| 生命周期 | 插件重载、20 次前后台、离线重连、账号/库切换 | 单任务互斥，迟到响应不提交到新上下文 |
| 隐私 | 配置、日志、诊断、配对、发布包 | 无令牌/会话秘密/签名 URL/正文泄露 |

每个拟开放档位至少做 10 次完整往返，记录平台、版本、源大小、峰值内存证据、磁盘峰值、请求数、吞吐、校验耗时和失败恢复结果。没有真实 iPad 测量就不把该档位列入 iPad 已支持范围。

测试里的“内存额度计数未超标”不能替代真实进程内存结果；没有可靠采样时标为未知。发布包仍只包含三个插件文件，测试样本、快照和报告不随包发布。

**LF-01～LF-03 的本地预检、跳过处理和按需分片范围已实现为 0.2.1 预览，168 项自动检查通过，仍保持 20 MiB。** 当前跳过清单是会话内最近成功扫描结果，不持久化路径；远端读端大小分离、真机内存与完整分块传输尚未实现。下一步先验证本版，再做 LF-04 平台原型，决定后续大小和平台，避免一次性重写全部引擎。

## 16. 依据与尚未确认事项

- 当前限制与调用链以文中列出的仓库源码为依据；这是 0.2.0 的代码事实，不是百度单文件限制。
- [Obsidian 官方 API](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)：二进制 API、追加接口及版本声明。不能据此推断 iPad 已具备流式读写。
- [百度网盘 SDK](https://github.com/baidu-netdisk/baidu-drive-sdk-go)：预创建、分片上传、提交和下载流程参考。SDK 存在某方法不代表当前应用权限、JS 网络适配器或 iPad 可直接使用。
- [HTTP RFC 9110 范围请求](https://www.rfc-editor.org/rfc/rfc9110.html#name-range)：范围与条件请求规则，不证明百度每个下载入口都支持。

待原型确认：应用真实分片/续传能力、下载链接的 Range 与对象验证器、移动端有界读写及取消、跨平台提交保证、实际内存与磁盘峰值。未确认前不提高默认上限、不承诺支持 GB 文件，也不引入第三方凭据或开发者服务器。
